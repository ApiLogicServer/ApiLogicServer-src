# Assessment: demo_mcp_send_email vs. reference implementation

Comparison of this build (`demo_mcp_send_email/`) against the shipped reference
implementation (`samples/demo_mcp_send_email/`), both created from the identical prompt
(`docs/requirements/project_creation_prompt.md`).

## Verdict

**Functionally equivalent, fully compliant with CE structure, and one real correctness
improvement over the reference.** Two minor hygiene defects found — neither in the logic
this session authored.

---

## 1. Schema — identical

`database/models.py` is byte-identical apart from the timestamp/db-path comment (both have
`Customer`, `Product`, `Supplier`, `Order`, `ProductSupplier`, `SysEmail`, `Item`). Same for
`database/mcp_models.py`, `database/mcp_db.sqlite`, and the full MCP infra tree
(`integration/mcp/*`, `api/api_discovery/mcp_discovery.py`, `ui/admin/mcp_admin.yaml`,
`docs/mcp_learning/*`) — added via `genai-logic genai-add-mcp-client`, not hand-authored, in
both builds.

## 2. check_credit.py — identical rule set

Both declare exactly: `Rule.sum(Customer.balance)`, `Rule.sum(Order.amount_total)`,
`Rule.formula(Item.amount)`, `Rule.copy(Item.unit_price)`, `Rule.constraint(balance <=
credit_limit)`. Only cosmetic differences (one-line vs. multi-line formatting, error-message
wording "exceeds credit" vs. "exceeds credit limit"). No behavioral difference.

## 3. send_email.py — this build is arguably *more correct*

| | This build | Reference |
|---|---|---|
| Rule type | `Rule.after_flush_row_event` | `Rule.commit_row_event` |
| Insert guard | `if not logic_row.is_inserted(): return` | none |

The requirement is explicit: *"When a SysEmail is created, log 'email sent'..."* — i.e., on
**insert** only. The reference's `commit_row_event` has no insert guard, so it will re-fire
"email sent" / "email blocked" on any later **update** to an existing `SysEmail` row (e.g.
editing its subject) — a latent over-firing bug relative to the literal requirement wording.
This build's `is_inserted()` guard avoids that. Both forms are documented valid patterns in
this project's own CE (the project CE's "Adding events" example uses `commit_row_event`;
`RequestObjectPattern.md`'s `SysEmail` example uses `after_flush_row_event`) — this build
picked the one that actually matches "when created," and said so explicitly in its own
ad-libs FYI.

## 4. MCP client — both use the generic CLI tool, no hand-authored logic

Neither build wrote custom MCP-interpretation code; both correctly ran `genai-logic
genai-add-mcp-client` and relied on the generic `mcp_client_executor.py` /
`mcp_client_executor_request.py` (byte-identical in both). This build additionally wrote
`docs/requirements/mcp_client/requirements.md` (verbatim excerpt of the 3rd prompt section)
— the reference did not create a per-use-case requirements.md for this section. Minor
traceability improvement, not required by CE since no `logic_discovery/mcp_client.py` file
was authored.

## 5. Provenance / ad-libs — both complete, different formats

`project_creation_prompt.md` content is identical (only bullet-indentation style differs).
`ad-libs.md` and `project_creation_report.md` differ in format (this build used the fuller
XRD-style Pre-Coding-Analysis / Diagnostic-Appendix / Error-Correction-Loop structure; the
reference used a shorter numbered-ad-libs format) but cover the same ground — both correctly
report **zero 🔴 Review Required items**, which is accurate: this spec has no grandfather-clause
or absence-of-event traps to miss.

## 6. Defects found (neither in the authored logic)

**a. Misplaced transcript file.** `demo_mcp_send_email/demo_mcp_send_email/transcript.md` — a
raw terminal-session capture (Claude Code banner, `/model` command history, etc.) landed in a
stray subdirectory literally named after the project itself, duplicating the project name as a
path segment. It isn't in the CE's mandated transcript format
(`.github/rfi_transcript_format.md`) and isn't linked from `project_creation_report.md`. Not
present in the reference. **Recommend deleting it** (or moving its content into
`docs/requirements/` if the transcript itself is wanted).

**b. Mangled `readme.md` (inherited from the live Docs fetch, not authored this session).**
`readme.md` is always re-fetched live from `raw.githubusercontent.com` via `copy_md()` (per
`dev-architecture.md`'s README propagation rule), not generated by this build. Compared to the
reference copy, this build's fetch has:
- Both CSS selectors in the `<style>` block lost their leading `.` — `.md-typeset` →
  `-typeset`, `.md-content__button` → `-content__button` — breaking the intended "hide
  duplicate H1 / content button" styling.
- The "🤖 Bootstrap your AI Assistant" line duplicated (once as bold text, once as the code
  block's `title=`).
- A stray duplicated "for readme," substring in the front-matter `version:` line.

This reproduces reliably from the live fetch and isn't something this session's logic
authoring touched — worth flagging upstream (Docs repo / `copy_md()`'s mkdocs→markdown
conversion), not something to "fix" locally.

## 7. Non-issues (observed, explained, not defects)

- `instance/`, root-level `__pycache__/`, `.idea/` present in this build but not the
  reference — artifacts of this build's server actually having been started and exercised
  live (matches its ad-libs' verification claims); the reference copy's absence of these
  suggests it was either cleaned up or never server-started.
